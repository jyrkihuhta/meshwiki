# Grinder Pre-flight: `__pycache__` Hygiene

When the factory runs `pytest` on a worker branch, cpython writes `__pycache__/*.pyc`
files alongside every imported module. Without a `.gitignore` rule those files
show up in `git status` as unstaged changes, blocking `git rebase origin/staging`
with `cannot rebase: You have unstaged changes` and forcing a wasteful
`git stash && git rebase && git stash pop` round-trip.

## What is configured

The root `.gitignore` lists (see `__pycache__/`, `__pycache__/**`, `*.pyc`,
`*.pyo`, `*.pyd`, `*.py[cod]`) so every bytecode artefact is ignored at the
moment it is written. There are no tracked `__pycache__/` directories or `.pyc`
files in the repository.

## Verification

`src/tests/test_gitignore.py` enforces the contract:

- `test_gitignore_excludes_pycache_artifacts` — `git check-ignore` returns 0
  for representative `__pycache__/*.pyc` paths in `src/`, `orchestrator/`,
  and the repo root.
- `test_gitignore_has_pycache_directive` — root `.gitignore` contains a
  top-level `__pycache__/` rule.
- `test_gitignore_has_pyc_extension` — root `.gitignore` contains `*.pyc`.
- `test_no_tracked_pycache_files` — `git ls-files` returns no
  `__pycache__` paths and no `.pyc` paths.
- `test_pytest_run_leaves_no_untracked_pycache` — after producing a
  `__pycache__/` directory and `.pyc` file in a temp dir, the porcelain
  output of `git status` contains no `__pycache__` or `.pyc` lines.

## Run before rebase

If a `.pyc` file slips into `git status` (for example generated by a tool
that runs before `.gitignore` was tightened), clear it with:

```bash
git clean -fdX __pycache__ tests/__pycache__ tests/fixtures/__pycache__
```

The `-X` flag removes **only** files matched by `.gitignore`, so untracked
source files (for example a brand-new module dropped into `src/`) are safe.

No `git stash` is required once this pre-flight has been run.
